# Загрузка навыков в облачной среде

В репозитории сохранены **33 проектных навыка**: `.agents/skills/<name>/SKILL.md`.
Источники, версии и файлы зафиксированы в [реестре](skills-lock.json), лицензии — рядом
с исходниками. Это набор инструкций для разработки, а не зависимости приложения.
Повторная установка пакетов для чтения навыков не нужна.

`.gitignore` явно включает два закреплённых font-index JSON Impeccable: прежнее общее
правило `data/` исключало их при добавлении в Git. `.gitattributes` сохраняет исходные
байты сторонних навыков, включая CRLF и upstream-пробелы; SHA-256 остаётся главным
контролем этих файлов. Для проектного навыка и конституции обычные whitespace-проверки
сохранены. Проверка экспорта Git сначала воспроизвела потерю этих двух файлов, затем
повторена после исправления.

## Что проверяется отдельно

| Уровень | Проверка | Состояние в текущей среде |
|---|---|---|
| Файлы | Пути, SHA-256, оригинальные лицензии, полный YAML, имена и описания | 33 навыка проверены; см. [отчёт подключения](skills-connection-validation.json) |
| Каталог Codex | Штатный загрузчик видит имена, описания и пути из нужного repo cwd | BLOCKED до загрузки, служебный профиль read-only |
| Применение | Агент читает навык и выполняет безопасную задачу по его правилам | В текущей беседе применены systematic-debugging и verification-before-completion через явное чтение файлов |
| Новая сессия | Независимый запуск агента с проектным каталогом | Попытка `codex exec --ephemeral --sandbox read-only` завершилась до старта сессии |
| Новая облачная задача | Восстановленный commit, каталог навыков и безопасная задача | Требует сохранения/публикации среды и отдельной проверки пользователем |

Явное чтение файла работает независимо от каталога навыков. Оно не доказывает, что вызов
`$skill-name` будет штатно разрешён новым клиентом. Имена в JSON-реестре также не являются
ответом загрузчика Codex.

## Причина блокировки и рабочий каталог

У `/workspace/EP-Base/.agents/skills` разрешено чтение; сам проект находится на writable
файловой системе. `/run/codex-environment/codex-home` смонтирован read-only, а файл
`installation_id` отсутствует. Codex 0.159.2 пытается создать его с `O_RDWR|O_CREAT` и
получает `EROFS (os error 30)` ещё до обнаружения навыков. Это подтверждено диагностикой
системного вызова и повторными запусками штатного prompt renderer и новой сессии.
Отдельный app-server также не может инициализировать SQLite state в этом служебном профиле
и не отвечает на запрос `skills/list`; неудачи происходят до разбора проектных навыков.
Обычная смена прав файлов не исправляет read-only mount.

Профиль, HOME/CODEX_HOME, защищённые `.agents`/`.codex`, sandbox и монтирования менять
для обхода нельзя. Разрешение на запись в проект не устраняет ограничение служебного
профиля. Нужен штатный запуск клиента с рабочим служебным профилем со стороны платформы.

Вторая независимая предпосылка: нативную сессию нужно начинать **в корне репозитория**,
здесь `/workspace/EP-Base`. Поиск от `/workspace` по родительским каталогам не включает
дочерний `.agents/skills` этого проекта. Выполненный позже shell `cd` не подтверждает
перезагрузку каталога уже открытого агента. Не копируйте набор в защищённый глобальный
каталог ради его обнаружения.

## Сохранённая настройка

- `scripts/cloud-skills-setup.sh` проверяет уже существующие файлы без npm, сети и БД.
  Его можно запускать из любого каталога: путь к проекту вычисляется от самого скрипта.
- [CLOUD_START.md](CLOUD_START.md) — содержимое стартовых инструкций облачного черновика:
  рабочий каталог, выбор нужного навыка, правила Spec Kit и безопасный fallback чтения.
- Скрипт установки в черновике вызывает только эту проверку. Он не переустанавливает
  зависимости приложения, Specify/Playwright или Impeccable engine. Уже установленные
  инструменты сохраняются в текущем workspace; их наличие в другой среде проверяется
  отдельно для конкретной задачи. Для самого каталога навыков они не нужны.
- Список репозиториев в черновике привязан к фактическому локальному commit и `EP-Base`.
  Сохранение черновика не является его применением или публикацией сайта.

Git-коммит сохраняет набор и правила в истории данного checkout. Он не означает push.
Текущий сервис среды предупреждает, что восстановление **локальных, ещё не отправленных
коммитов** не поддерживается надёжно. Snapshot и сохранённый SHA поэтому не доказывают
доступность набора в следующей задаче. Не подменяйте SHA удалённой веткой и не делайте push
только ради обхода этой проверки. Посторонние изменения приложения в skill-коммит не входят.

## Проверка после сохранения среды

1. В настройках этой облачной среды откройте сохранённые изменения (Review): проверьте
   repository `vlasov3202-blip1/EP-Base`, mount path `EP-Base`, SHA из итогового отчёта,
   setup script и start instructions. Нажмите **Save**, затем **Publish** среды.
   Это публикация конфигурации и снимка среды, не сайта EINEIRO.
2. Создайте **новую задачу** в опубликованной среде с этим репозиторием. Используйте
   [готовый текст безопасной проверки](SKILL_SMOKE_PROMPT.md). Сопоставьте `git rev-parse HEAD`
   с SHA из отчёта; если коммит не восстановился, проверка сохранности не пройдена.
3. В новом клиенте проверьте начальный каталог навыков: ожидаются 33 проектных имени
   из реестра с путями внутри этого checkout. Для CLI/IDE начинайте с корня проекта.
   Если каталог отсутствует, отчёт должен явно отличать чтение файлов от native discovery.
4. Примените выбранный навык к проверке реестра. Успех — фактический результат команды,
   правильный вывод по правилам навыка и подтверждение наличия навыка в начальном каталоге.
   Наличие `SKILL.md` само по себе не завершает проверку.

Для самостоятельного CLI с исправным штатным профилем эквивалентный запуск:

```bash
cd /workspace/EP-Base
codex exec --ephemeral --sandbox read-only --cd /workspace/EP-Base --json - \
  < docs/SKILL_SMOKE_PROMPT.md
```

В текущем контейнере эта команда блокируется служебным профилем. Если после Publish и
новой задачи повторяется `EROFS` для `installation_id`, в обращении поддержке среды укажите
Codex 0.159.2, указанный путь, mount read-only, отсутствие файла и отказ до создания сессии.
Не отправляйте auth/config файлы или секреты. Исправление относится к запуску среды, а не
к повторной установке навыков. Если новый checkout не содержит локальный commit, нужен
поддерживаемый платформой перенос истории либо отдельное согласованное сохранение в remote.
