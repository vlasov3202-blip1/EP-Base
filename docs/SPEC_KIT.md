# Spec Kit в EINEIRO

Установлен официальный [GitHub Spec Kit](https://github.com/github/spec-kit), релиз
**1.2.2**, коммит `74be0a63e93c7087c5b06556b7561810d8f78a45`, лицензия
[MIT](../.specify/LICENSE). Коммерческое использование разрешено с сохранением лицензии
и авторского уведомления при распространении соответствующих материалов.

## Установка и состав

- Десять штатных Codex-навыков: `.agents/skills/speckit-*/SKILL.md`.
- Шаблоны, Bash-скрипты и штатный workflow: `.specify/`.
- [Конституция 1.0.0](../.specify/memory/constitution.md) фиксирует принятые правила
  EINEIRO, ограничения Silent Run и проверки разработки.
- [Манифест](spec-kit-lock.json) фиксирует источник и SHA-256 установленных upstream-файлов.

Официальный CLI построен из закреплённого релиза. Scaffold сгенерирован в отдельном
временном каталоге и перенесён после проверки отсутствия конфликтов. Прежние файлы навыков
сохранены. Дополнительные расширения, пресеты и runtime event hooks не включались.
Штатные команды и шаблоны сохранены без правок; конституция является документом проекта.

CLI текущей облачной среды: `/workspace/.tools/bin/specify`. Для восстановления CLI
на другой машине с Python 3.11+ и `uv`:

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@74be0a63e93c7087c5b06556b7561810d8f78a45
```

В этой облачной среде, где запись в домашний каталог ограничена, используйте:

```bash
UV_TOOL_DIR=/workspace/.tools/uv UV_TOOL_BIN_DIR=/workspace/.tools/bin \
  UV_CACHE_DIR=/workspace/.cache/uv \
  uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@74be0a63e93c7087c5b06556b7561810d8f78a45
export PATH="/workspace/.tools/bin:$PATH"
```

Повторная инициализация поверх текущего проекта не нужна. Обновление версии выполняется
отдельно с просмотром изменений и сохранением конституции. В уже открытом клиенте может
потребоваться новая сессия для обнаружения навыков; их инструкции доступны напрямую по путям.

## Следующая механика

1. `$speckit-specify` — описать запрошенную механику, сценарии, права, ошибки и критерии
   приёмки. Первая задача будет создана из следующего конкретного задания пользователя.
2. `$speckit-clarify` — уточнить только существенные нерешённые требования, если они есть.
3. `$speckit-plan` — составить план на основе текущей архитектуры EINEIRO.
4. `$speckit-tasks` — разложить реализацию и необходимые проверки на задачи.
5. `$speckit-analyze` — проверить согласованность требований, плана и задач.
6. `$speckit-implement` — выполнить согласованную работу и проверки.
7. `$speckit-converge` — сверить реализацию с документами, затем закрыть обнаруженные пробелы.

Обычный режим — выполнение нужного навыка в текущей сессии. Штатный автоматический runner
с review gates доступен как upstream-возможность, но не запущен и не является обязательным
для каждой задачи. Установка навыков не создаёт автоматически feature-ветки, коммиты или
GitHub Issues. `speckit-taskstoissues` включён upstream как устаревающая команда и не входит
в наш обычный процесс; публикация задач требует явного задания пользователя.

Для небольших исправлений полный цикл не нужен. Дизайн-навыки применяются в соответствующих
задачах реализации. Проверки приложения берутся из `AGENTS.md`, а не из примеров шаблона.

В реализации используются выбранные `test-driven-development`, `systematic-debugging` и
`verification-before-completion`; для изменения данных — проектный `eineiro-safe-migrations`.
Они дополняют задачи и проверки текущей спецификации. Полный процесс Superpowers не включён.
Маршрутизация и приоритет правил: [SKILLS.md](SKILLS.md).

## Хранение требований

Каждая существенная механика получает `specs/<number>-<feature>/spec.md`, `plan.md` и
`tasks.md`. Дополнительные документы нужны только при реальной сложности задачи.
Завершённая спецификация остаётся действующим контрактом: при согласованном изменении
поведения обновляем её и связанные план/задачи, сохраняя историю в Git. Существующие
канонические документы остаются источником продуктовых правил.

`converge` и отметки задач не доказывают production-готовность. В отчёте указываются
реально выполненные проверки, ограничения моков и непроверенные внешние интеграции.

Исходная инструкция: [внедрение в существующий проект](https://github.com/github/spec-kit/blob/v1.2.2/docs/guides/existing-projects.md).
